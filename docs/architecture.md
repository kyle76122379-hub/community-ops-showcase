# 운영 구조

## 전체 구성

```
[안드로이드 기기 1대]
  ├── 부팅 스크립트        → 재부팅 시 자동 실행
  ├── keepalive.sh         → 20초 주기로 상태 점검, 죽은 프로세스만 재기동
  ├── 봇 (discord.py)      → 기능 모듈 37개 로딩
  ├── 웹 (FastAPI)         → 관리 화면 37개, Discord OAuth 로그인
  └── 터널                 → 외부 HTTPS 접속 (인증 필요)
```

## 왜 이 구조인가

- **서버 임대 비용 0원.** 남는 기기에서 돌려 운영 비용을 없앴습니다. 대신 "언젠가 죽는다"는 문제를 반드시 해결해야 했습니다.
- **복구를 기능처럼 다뤘습니다.** 크래시 원인을 없애는 것보다, 죽으면 20초 안에 다시 올라오는 구조가 실사용에서 더 빨랐습니다.
- **PID 재사용 방어.** 워치독이 이미 실행 중인지 판단할 때 PID만 보면 재사용된 다른 프로세스를 자기 것으로 오인합니다. `/proc/<pid>/cmdline`까지 확인해 keepalive.sh인지 검사합니다.

## 설정 일관성

봇과 웹이 같은 값을 보도록, 길드별 설정은 `core/*_settings.py`의 스키마 한 곳에서 정의합니다.

- 기본값 · 검증 규칙 · 허용 범위를 스키마에 선언
- 웹은 이 스키마를 읽어 화면을 만들고, 봇은 같은 값을 읽어 동작
- 값을 바꾸면 다음 명령부터 즉시 반영(재시작 불필요)

## 데이터 흐름 (스크림 예시)

```
투표(디스코드) → 집계 → 최다 득표 슬롯 확정 → 게시판 글 갱신
                                  → 캘린더 등록 → 3분 주기 재확인
                                  → 빈자리(4/5)일 때만 용병 모집 글 게시
```

## 실패했던 접근

- **처음: 거대한 기능을 한 번에 요청.** AI가 만든 코드가 서로 맞물리지 않아 고칠수록 나빠졌습니다. → 기능 단위로 쪼개고, 한 번에 가설 하나만 검증하는 방식으로 바꿨습니다.
- **프로세스 감시 명령이 기기에서 동작하지 않음.** 데스크톱 리눅스 기준 설명을 그대로 쓴 명령이 이 환경에서 프로세스를 찾지 못했습니다. → 기기에서 직접 확인한 뒤 다른 방식으로 교체했습니다.
